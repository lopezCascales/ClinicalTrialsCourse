## Where clinical data comes from

Clinical data is a byproduct of care delivery, generated across several distinct points in the healthcare
system:

- **Clinical encounters** — notes, orders, diagnoses and procedures entered by clinicians during a visit
  or admission, most often stored in an Electronic Health Record (EHR).
- **Laboratory and diagnostic systems** — lab results, pathology, radiology reports and images, generated
  by ancillary systems and typically fed into the EHR via interfaces (e.g. HL7 messages).
- **Billing and administrative systems** — claims data, generated for reimbursement purposes rather than
  clinical documentation, using standardized codes (e.g. ICD-10 diagnosis codes, CPT procedure codes).
- **Devices and monitors** — vitals, continuous monitoring data, increasingly wearables — often
  high-frequency, time-series data.
- **Patient-reported data** — patient portals, questionnaires, patient-reported outcome measures (PROMs).

Because each of these is generated for an operational purpose (documentation, billing, monitoring) rather
than for research, all of them carry the biases and gaps of their original purpose when reused for analysis
— this is the central theme of "secondary use" of clinical data.

## What clinical data looks like

### Structured vs. unstructured data

- **Structured data**: discrete, coded fields that can be queried directly — diagnosis codes (ICD-9/10),
  procedure codes (CPT, HCPCS), lab results with standardized identifiers (LOINC), medications (RxNorm,
  NDC), demographics, vital signs.
- **Unstructured data**: free text — clinical notes, discharge summaries, radiology/pathology reports.
  This is often the majority of the clinically meaningful content in an EHR, but requires natural language
  processing (covered later in this course, in the "Clinical Natural Language Processing" module) to
  extract systematically.
- **Semi-structured data**: data with some structure but requiring parsing — e.g. templated notes,
  structured fields embedded in otherwise free-text documents.

### Data provenance and its consequences

Because clinical data is generated by many different systems and people, over long and irregular time
spans, provenance (who/what generated a given data point, and why) directly affects data quality:

- **Timing is irregular**: patients are observed only when they interact with the healthcare system, not
  on a fixed schedule — this creates informative censoring and irregular time series.
- **Coding is inconsistent**: the same clinical concept can be coded differently by different clinicians,
  institutions, or coding systems, and code use changes over time as standards are updated.
- **Missingness is rarely random**: the absence of a data point (e.g. a lab test never ordered) is often
  informative in itself, rather than a random gap.

### Common data models

To reuse EHR data across institutions for research, several standardized "common data models" have been
developed to reshape heterogeneous EHR data into a shared structure — for example the **OMOP Common Data
Model** (Observational Medical Outcomes Partnership, maintained by OHDSI) and **HL7 FHIR** (Fast Healthcare
Interoperability Resources) for data exchange. This course's "Clinical Data Models and Data Quality
Assessments" module covers OMOP directly, using the MIMIC-III dataset as a working example.
